# Study Assistant Chatbot — Implementation Plan

> **⚠️ Written as a plan, kept as a record. Updated 2026-08-19 for the Groq → Gemini
> migration** (Prompt 4 of `MIGRATION_PROMPTS_GEMINI.md`). Everything below now describes
> what was actually built, not what was proposed; the sections marked *historical* record
> decisions that were later reversed and are kept because the reasoning still matters.
> §"Groq → Gemini migration" at the end carries the measurements.

## Overview

The chatbot in `ResourcesTab.tsx` allows students to have a contextual conversation about their uploaded study materials. Instead of re-sending entire PDFs on every message, we use **Retrieval-Augmented Generation (RAG)** — the concepts already extracted and embedded in the `concepts` table are used as the knowledge base for the AI to answer questions.

## AI Model Decision

| Concern | Choice | Reason |
|---|---|---|
| **Chat model** | **Gemini — `gemini-3.5-flash-lite`** (`GEMINI_CHAT_MODEL`), at `ThinkingLevel.MINIMAL` | The fastest and most *consistent* model measured across the whole migration — 1.8 / 2.1 / 1.8 / 1.9 / 1.9s over five samples, where `gemini-3.6-flash` swung between 2s and 20s on identical requests. Time-to-first-token is what a chat UI is judged on, so consistency matters more here than raw capability. It is also the cheap model: chat is the highest-volume workload in the app (~1,500 calls in the study's cost estimate, more than every other feature combined). **Chat is conversational rather than authoritative** — a student can push back on an answer mid-conversation, which is exactly what they cannot do with a test question — so it does not need `GEMINI_CONTENT_MODEL`. |
| **Embedding** | **Gemini — `gemini-embedding-001`** | **Note on Gemini 1 vs 2:** Because your current database already contains vectors generated by `gemini-embedding-001` (when the documents were first uploaded), we *must* use the exact same model to search. If we used `002` for the chat, the math wouldn't match up and the search would fail. If you want to upgrade to `002` later, we would have to wipe the database and re-parse all PDFs. |
| **Streaming** | Yes — `streamContent()` in `server/lib/gemini.ts` | **What this means:** normally you wait 5–10 seconds for an AI to write a full paragraph before anything appears. "Streaming" sends text to the screen as it is generated, so the student is never staring at a spinner. This is the **only streaming call in the codebase** — `generateJson()` and `generateContent()` both wait for a whole response, which is right for authoring work and wrong here. |

> **📛 HISTORICAL — this table used to say the opposite, and the reversal is worth keeping.**
> The original decision was **Groq `llama-3.1-8b-instant`**, chosen because Groq was
> *significantly faster* (sub-second first token) and Gemini was used only to embed the
> query. That was true when it was written. Groq then **decommissioned both
> `llama-3.1-8b-instant` and `llama-3.3-70b-versatile` on 17 June 2026** — verified against
> our own key: *"The model does not exist or you do not have access to it"* — and closed its
> paid tier to new signups, so it could not have scaled to the 50-student study regardless.
> **The chatbot was broken in production from June until 19 August 2026.**
>
> The old "saves token limits" argument is also gone. Groq's free tier metered **tokens per
> minute**; Gemini's meters **requests per model** (5/min and 20/day on the free key), so
> picking a smaller model no longer saves anything on the same bucket — but `gemini-3.5-flash-lite`
> has its **own** bucket, separate from the `gemini-3.6-flash` one that tests, flashcards and
> games share. That, not token size, is why a distinct model is still the right call.

## Architecture: Hybrid RAG System

To address your excellent question: *"If the student asks to summarize the entire document, does the bot only retrieve 8 concepts?"*

If we only used embeddings, yes, it would only retrieve 8 concepts and give a terrible summary! To fix this, we will use a **Hybrid Approach**:

1. **Specific Questions ("What is RA 10175?"):** We use the embedding model to search and retrieve the Top 8 most relevant concepts. This is fast and saves tokens. (`mode: 'rag'`)
2. **"Summarize" / "Explain Simply" buttons:** We completely bypass the embedding model and fetch **ALL** concepts for the selected document, so the summary covers the whole thing. (`mode: 'full'`)

**Two things were added during implementation that this plan did not anticipate**, and both
still hold after the Gemini migration:

3. **A typed "summarize this file" is routed to full mode too.** `isDocumentLevelRequest()`
   in `chat.routes.ts` matches phrases like *summarize · TL;DR · overview · key points ·
   explain this*, so typing the request behaves the same as clicking the button. Without it
   these were wrongly refused: they carry no topical keywords, so their embeddings are
   generic and score poorly against individual concept vectors.
4. **Off-topic questions are refused deterministically, with no model call at all.** Two
   thresholds, both calibrated empirically against a cybersecurity material:
   - `RAG_MATCH_THRESHOLD = 0.60` — off-topic queries (a K-drama plot, a cookie recipe) top
     out near **0.48**; genuinely on-topic questions land at **~0.70+**.
   - `DOC_LEVEL_MATCH_THRESHOLD = 0.51` — a real "summarize this file" scores **~0.53–0.60**,
     while a summary request whose real subject is external ("summarize the life lessons from
     *Reply 1988*") scores **~0.46–0.50**. The gate sits in that gap.

   ⚠️ **Both numbers survived the move to Gemini unchanged, and that is not an oversight.**
   They gate cosine similarity between *embeddings*, and the embedding model is fixed at
   `gemini-embedding-001`. Changing which model writes the reply cannot move them.

```
Student action determines the flow:
        ↓
IF specific question: 
  → Embed query → Find Top 8 concepts via cosine similarity
IF clicked 'Summarize': 
  → Fetch ALL concepts for the selected files directly
        ↓
Assemble concepts as CONTEXT
        ↓
Gemini gemini-3.5-flash-lite streams the response back as it writes
        ↓
Backend saves the conversation to the `chatbot_logs` table
```

## Proposed Changes

### Backend

---

#### [NEW] `server/routes/chat.routes.ts`

A brand-new route file dedicated to the chatbot. Contains:

**`POST /api/chat`**

Request body:
```json
{
  "message": "What is RA 10175?",
  "material_ids": ["22a83138-...", "32b615c9-..."],
  "history": [
    { "role": "user", "content": "Hello" },
    { "role": "assistant", "content": "Hi! Ask me anything..." }
  ]
}
```

Logic, as shipped:
1. **Auth gates first.** `router.use(authenticate, requireRole('student'))` covers **both**
   routes in the file. ⚠️ This was missing originally — both routes ran on `authenticate`
   alone, so an educator or admin could drive the student chatbot and neither route checked
   `profiles.status`. It became load-bearing when the first-login gate landed, since
   `requireRole` is the only middleware that reads `profiles`.
2. Validate the request body with Zod (`ChatRequestSchema`).
3. **Ownership and access.** The space must belong to the caller (**404** otherwise), then
   `rejectInaccessibleMaterials()` on the body's `material_ids` (**403** otherwise). The reply
   recites the text of those materials, so this is a read of them and is gated the same way —
   without it a student could pass any material id and have the assistant read out another
   grade's content.
4. Embed the student's message using `generateEmbedding()` (Gemini) — RAG mode only.
5. Call the `match_concepts` RPC for the top 8 concepts by cosine similarity, then apply the
   thresholds above: refuse, route to full mode, or keep the hits.
6. Cap the knowledge base at **`MAX_CONTEXT_CHARS = 32,000`** via `fitContext()`, which drops
   whole concepts from the end — never mid-definition — and trims the concept list itself, so
   `source_concept_ids` records what genuinely grounded the answer.
7. Build the prompt: the grounding rules as the **system instruction**, plus the **last 4
   messages** of history and the current query. ⚠️ Gemini has **no system role inside
   `contents`**, so the system prompt travels separately; and Gemini calls the assistant turn
   `model`, not `assistant`.
8. Call **`streamContent()`** with `GEMINI_CHAT_MODEL`, `ThinkingLevel.MINIMAL` and
   `maxOutputTokens: 4096`.
9. Pipe it to the client as Server-Sent Events with `res.write()` —
   `data: {"token": "…"}` per chunk, then `data: {"done": true}`, then `res.end()`.
10. Save the prompt and the assembled response into **`chatbot_logs`** *after* the stream
    completes. A failed log write is a `console.warn` and never costs the student the answer
    they just read.

**⚠️ The stream is opened BEFORE the SSE headers are flushed, and the order is load-bearing.**
`streamContent()` awaits the upstream request, so a refusal — a spent daily quota above all —
arrives while a real HTTP status is still sendable (429 for quota, 503 for an outage). The
route used to flush headers first, which made its own `!res.headersSent` branch unreachable
and turned every failure, whatever the cause, into the client's generic *"something went
wrong."* A failure **mid**-stream still emits `data: {"error": "Stream interrupted"}`, because
by then there is no status left to send.

#### [MODIFY] `server/lib/gemini.ts`

Originally *"no changes needed — `generateEmbedding()` already exists"*. That stopped being
true on 2026-08-19: **`streamContent()` was added here**, and it is the only genuinely new
code in the whole five-prompt Groq migration — every other workload mapped straight onto the
existing `generateJson()`.

```ts
streamContent({ model, systemInstruction, history, message, thinkingLevel, maxOutputTokens })
  → Promise<AsyncIterable<string>>
```

Three rules inside it, each with a reason:

- **It awaits the stream's opening and returns the iterator — it is deliberately NOT an
  `async function*`.** `generateContentStream()` issues the HTTP request itself and its
  promise rejects on the initial failure, before any chunk exists. Written as a generator,
  that rejection would be deferred to the caller's first `for await`, which happens after the
  headers are flushed — the exact failure described above. Awaiting the open is what keeps a
  typed error reachable. *Verified: a bogus model name rejects with zero chunks yielded.*
- **`withRetry()` wraps the opening ONLY.** Retrying is safe there precisely because nothing
  has been yielded. A failure *during* iteration must never be retried — the client already
  holds half an answer, and a second attempt would splice itself into the middle of a
  sentence.
- **A `MAX_TOKENS` finish is logged.** `describeEmptyResponse()` cannot help here: a truncated
  *stream* throws nothing and returns no empty response, it simply stops mid-sentence, and the
  only symptom is a student saying the assistant cut off.

It reuses `withRetry()`, `GeminiUnavailableError` and `GeminiQuotaError` unchanged, so a chat
failure is classified exactly like every other Gemini call in the app.

#### ~~[MODIFY] `server/lib/groq.ts`~~ — RETIRED

*Historical.* This section added `streamChatCompletion()`, wrapping
`groq.chat.completions.create({ stream: true })` on `llama-3.1-8b-instant` with
`temperature: 0.6` and `max_tokens: 2048`. It was deleted on 2026-08-19.

- **`temperature` is gone, not ported.** Gemini 3 dropped the sampling parameters entirely.
  Nothing is lost here — unlike Free Recall and Feynman, no chat output is scored, so there is
  no reproducibility guarantee that needed compensating.
- **`max_tokens: 2048` became `maxOutputTokens: 4096`.** MINIMAL thinking is not *no* thinking,
  and Gemini 3 thinking tokens draw on the same budget. Measured: the longest realistic reply
  (a whole-document summary over 28 concepts) runs 2,500–4,100 characters and finishes
  naturally; doubling the ceiling to 8,192 produced a *shorter* answer, confirming 4,096 is not
  binding.
- `streamChatCompletion()` was **the last Groq caller in the codebase**. With it gone nothing
  imports `groq.ts`, so the module is never loaded and `[Groq] key loaded` no longer appears in
  the boot log. Prompt 5 deletes the file, `groq-sdk` and `GROQ_API_KEY`.

#### [NEW] Supabase Migration — `match_concepts` RPC

A PostgreSQL function does the vector similarity search. **As shipped** (see `schema.sql`) it
differs from the draft in two ways: it returns the concept **`id`**, which is what
`chatbot_logs.source_concept_ids` records, and it takes a **`match_threshold`** parameter:

```sql
CREATE OR REPLACE FUNCTION match_concepts(
    query_embedding vector(3072),
    material_ids    UUID[],
    match_count     INT   DEFAULT 8,
    match_threshold FLOAT DEFAULT 0.0
)
RETURNS TABLE (
    id         UUID,
    term       TEXT,
    definition TEXT,
    similarity FLOAT
)
LANGUAGE sql
STABLE
SET search_path = public
AS $$
    SELECT
        id,
        term,
        definition,
        1 - (embedding <=> query_embedding) AS similarity
    FROM concepts
    WHERE material_id = ANY(material_ids)
      AND embedding IS NOT NULL
      AND 1 - (embedding <=> query_embedding) >= match_threshold
    ORDER BY embedding <=> query_embedding
    LIMIT match_count;
$$;
```

> The route calls it with **`match_threshold: 0`** on purpose — it wants the raw scores so it
> can gate them in code against the two thresholds above, and a query filtered in SQL could not
> tell "nothing relevant" from "nothing at all".

> [!NOTE]
> This uses the `<=>` (cosine distance) operator from `pgvector`. Since your vector dimension (3072) exceeds the pgvector HNSW index limit of 2000, this is a sequential scan — acceptable for student-scale data sets.

   - `material_ids` — as shipped this is **exactly one**, `[chatMaterial.id]`, the material

   > than a word. Measured on the real route: a short RAG answer arrives in **4 chunks**, a

   > two or three writes is the transport being different, not streaming having broken.

- 📖 **Key Terms** — `mode: 'full'`
- ❓ **Quiz Me** — **`mode: 'rag'`**, because it asks for questions on *specific* concepts

## Groq → Gemini migration — 19 August 2026

Prompt 4 of `LearnSyncAI artifacts/MIGRATION_PROMPTS_GEMINI.md`. **The chatbot had been broken
in production since 17 June 2026**, when Groq decommissioned `llama-3.1-8b-instant`: every
message failed inside the streaming loop, *after* the headers had been flushed, so the student
saw the client's generic *"Sorry, something went wrong."*

### What moved

| | Before (Groq) | After (Gemini) |
|---|---|---|
| Model | `llama-3.1-8b-instant` | `gemini-3.5-flash-lite` (`GEMINI_CHAT_MODEL`) |
| Thinking | n/a | `ThinkingLevel.MINIMAL`, set explicitly |
| Sampling | `temperature: 0.6` | **deleted** — Gemini 3 dropped the sampling parameters |
| Output ceiling | `max_tokens: 2048` | `maxOutputTokens: 4096` |
| Transport | `streamChatCompletion()` in `groq.ts` | `streamContent()` in `gemini.ts` |
| Context limit | prose only — Groq 413'd past ~6,000 tokens | `MAX_CONTEXT_CHARS = 32,000`, enforced |
| Failure before first chunk | always an SSE error blob | real HTTP status (429 quota / 503 outage) |

**The SSE wire format did not change and the client was not touched.**

### The context limit that never existed

The rule *"only one material in full mode, because >6,000 tokens 413s"* was recorded in
`CLAUDE.md` and cited in `conceptExtraction.ts` as a reason for `MAX_MERGED_DEFINITION_CHARS` —
but **nothing in the code enforced it**. The real limit was Groq refusing, and what kept full
mode inside it was the client sending one material.

`gemini-3.5-flash-lite` takes ~1M input tokens, so the old figure is meaningless. It was
replaced with a real guard rather than removed: **32,000 characters (~8,000 tokens)**, about
5× what Groq accepted. Measured against live data, this is a runaway guard rather than a
working constraint — the largest material renders to **6,136 characters for 28 concepts**, and
the theoretical worst case is ~33,600 (42 concepts × the 800-character definition cap). *If it
ever starts firing, that is the signal that full mode is being pointed at more than one
material.*

### Verification — 19 August 2026, live server, throwaway student over real HTTP

Driven through the actual route so the whole middleware chain was exercised, not by calling the
helper directly.

**Auth gates** — educator token **403**, another student's space **404**, a material outside the
caller's grade **403**. None reached the model.

**Four conversations:**

| Request | First token | Total | Chunks |
|---|---|---|---|
| Off-topic refusal ("summarize the plot of *Reply 1988*") | 1.3s | 1.3s | 1 — **no model call** |
| RAG, specific question ("what is SQL injection?") | 2.1s | 2.3s | 4 |
| Typed "summarize this file" → routed to full | 2.1s | 5.1s | 35 |
| Full mode, carrying 2 prior turns | 1.7s | 2.8s | 16 |

Roughly **0.4s of each figure is auth and database round-trips** — the gate requests, which do
nothing else, took 356–653ms — so the model's own first token lands around **1.3–1.7s**, matching
the 1.8–2.1s recorded during model selection.

`chatbot_logs` wrote **4 rows** with the right `source_concept_ids`: `null` for the refusal, **6**
for the RAG answer, **28** for both summaries. Off-topic refusal still logs and still costs zero
model calls.

**Truncation check.** The whole-document summary came back at exactly 4,096 characters — the same
number as the token budget, which looked like a silent truncation. It was not: re-running the
same prompt gave 3,854 characters finishing on a complete sentence with no `MAX_TOKENS` finish,
and **doubling the budget to 8,192 produced a *shorter* answer (2,525 characters)**. Reply length
simply varies now that there is no `temperature` to pin it.

**Pre-header failure path.** Forced with a bogus model name: the promise rejects with **zero
chunks yielded**, so the route's JSON error branch is genuinely reachable.

`npm run lint` and `npx vite build` both clean. Confirmed in the browser by the developer: replies
stream progressively.
